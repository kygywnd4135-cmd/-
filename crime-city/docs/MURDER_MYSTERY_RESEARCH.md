# 머더 미스터리 온라인 플랫폼: 시장 조사 기반 설계 레퍼런스

> 이 문서는 개발 참고 자료다. 2026-11 기준으로 경쟁 플랫폼(우즈, 중국 剧本杀 앱, Hunt A Killer, Zoom형 등)의 소비자 리뷰를 분석해 **요구사항으로 변환**했다.
> 기능을 설계하거나 우선순위를 정할 때 이 문서의 `REQ-*` ID를 근거로 삼아라.
> 요구사항 ID에 붙은 출처는 본 문서 §6의 "근거 요약"에 정리돼 있다.

---

## 0. 한 줄 요약 (가장 먼저 읽을 것)

**머더 미스터리 시나리오는 "평생 1회 소비" 콘텐츠다.** 그래서 플랫폼의 핵심 과제는 "사람을 모으는 것"이 아니라 **"한 판을 끝까지 지키는 것"**이다.
경쟁사들은 GM-less 자동 진행과 매칭으로 모집 문제를 이미 풀었다. 남은 1순위 불만은 **중도 이탈, 노쇼, 무마이크, 트롤, 크래시로 판이 무산되는 것**이다.
→ 모든 설계 결정에서 "이 기능이 판 무산을 줄이는가?"를 먼저 물어라.

## 1. 용어 (Glossary)

| 용어 | 의미 |
|---|---|
| 머미 / 마다미스 / 剧本杀(쥐번샤) | 머더 미스터리. 플레이어가 캐릭터를 맡아 대화·추리로 범인을 찾는 스토리형 마피아 게임 |
| 시나리오 | 하나의 게임 콘텐츠. 인원 고정(예: 5인), 소요 1~5시간 |
| 핸드아웃(Handout) | 플레이어별 비공개 캐릭터 자료(배경, 비밀, 목표) |
| GM | 게임 마스터(진행자). 단계 전환, 단서 배포, 판정을 맡음 |
| GM-less | 앱이 GM 역할을 자동으로 수행 |
| 페이즈(Phase) | 진행 단계. 예: 읽기 → 자기소개 → 조사 → 토론 → 밀담 → 투표 → 엔딩 |
| 밀담 | 일부 플레이어끼리 나누는 비공개 대화 |
| 통과 | 해당 시나리오를 플레이 완료함. 통과한 시나리오는 플레이어로 재참가 불가 |
| 감상전 | 엔딩 이후 플레이어끼리 나누는 복기·감상 대화 |
| 테이블(卓) / 방 | 하나의 플레이 세션 |
| 성향 | 시나리오 성격. 추리형 / RP(롤플레이)형 / 감성형 / 코미디형 / 호러형 |

## 2. 도메인 불변 조건 (Invariants: 깨지면 안 되는 규칙)

1. **스포일러 격리:** 플레이어는 자기 핸드아웃과 공개된 정보만 볼 수 있어야 한다. 숨겨진 정보는 **서버가** 페이즈와 조건에 따라 공개한다. 클라이언트에 전체 데이터를 내려보내지 마라(불법복제 방지도 겸함).
2. **통과 기록은 영구적이다:** 통과한 시나리오는 플레이어로 다시 매칭되면 안 된다. 관전과 GM 참여만 허용한다.
3. **인원 고정:** 시나리오마다 정해진 인원이 다 차야 진행할 수 있다. 결원은 곧 판의 붕괴다. 그래서 결원 복구 수단(REQ-P0-1~3)이 필수다.
4. **세션 상태는 서버가 원본이다:** 클라이언트가 크래시하거나 기기를 바꿔도 같은 지점에서 복귀할 수 있어야 한다.
5. **리뷰·커뮤니티에서도 스포일러 금지:** 공개 영역에는 내용이 아니라 "성향"만 노출한다.

## 3. 요구사항 (우선순위별)

### P0: 없으면 경쟁사 불만을 그대로 반복함

| ID | 요구사항 | 구현 힌트 |
|---|---|---|
| REQ-P0-1 | **재접속 세이프 구간**: 끊긴 플레이어가 생기면 진행을 자동 일시정지하고 N분간 복귀를 기다린다. 다른 사람에게는 "재접속 중"으로 표시 | 세션 상태 머신에 `PAUSED_RECONNECT` 상태. 타이머가 만료되면 P0-2로 넘어감 |
| REQ-P0-2 | **AI 대타 플레이어**: 복귀하지 않으면 AI가 그 캐릭터의 핸드아웃을 바탕으로 이어서 플레이(텍스트 또는 TTS). 원래 플레이어가 돌아오면 다시 넘겨줌 | 캐릭터별 컨텍스트 = 핸드아웃 + 공개 로그 + 해당 캐릭터의 밀담 로그. **다른 캐릭터의 비밀은 컨텍스트에 넣지 않는다** |
| REQ-P0-3 | **신뢰 점수 + 보증금**: 참가할 때 소액 코인을 예치하고 완주하면 환급. 이탈하면 피해자들에게 분배. 반복 이탈자는 매칭 우선순위를 낮추거나 참가를 제한 | `User.trustScore`, `Session.deposit`. 이탈 원인 설문(누가 원인이었나)도 받는다 |
| REQ-P0-4 | **입장 전 체크 게이트**: 마이크·스피커 테스트, 예상 소요시간 동의, 네트워크 체크를 통과해야 입장 | 매칭 직전 단계에서 처리 |
| REQ-P0-5 | **음성 안정성**: 음성은 앱 로직과 격리된 인프라를 쓴다. 앱 크래시가 나도 통화는 유지 | WebRTC SFU(LiveKit 등). 음성 장애와 게임 상태 장애를 분리 |
| REQ-P0-6 | **단계적 차단**: 뮤트(그 사람의 모집글 숨김) → 차단 → 신고. 차단한 유저가 같은 방에 들어오면 경고. 기능은 눈에 잘 띄는 곳에 | 우즈 유저들이 "차단·신고를 찾기 어렵다", "더 가벼운 뮤트가 필요하다"고 요구 |
| REQ-P0-7 | **서버 측 정보 공개**: 핸드아웃과 단서는 페이즈 이벤트에 맞춰 서버가 개별 전송한다. 전체 시나리오 파일은 클라이언트에 두지 않음 | 불변 조건 1 |

## 4. 안티패턴 (하지 말 것)

- ❌ **자동갱신 구독을 기본값으로 두는 것**: Hunt A Killer 불만의 대부분이 "일시정지 후 예고 없이 재개", "해지했는데 결제됨"이다. 쓴다면 시즌 단위로 끝나게 하고, 갱신 전 알림과 원클릭 해지를 제공하라.
- ❌ **소셜·교우 기능으로 추리 경험을 덮는 것**: 중국 앱의 CP 만들기와 위치 권한 반복 요구가 피로를 낳았다. 소셜 기능은 선택 사항으로 둔다.
- ❌ **단일 별점 리뷰**: 스포일러 때문에 이유를 쓸 수 없어서, 작가 입장에서는 개선 정보가 없는 저평가만 쌓인다.
- ❌ **수량 위주의 시나리오 확장**: 검수 없이 늘리면 "유료인데 시간 낭비"라는 리뷰로 신뢰가 무너진다.
- ❌ **클라이언트에 전체 시나리오 번들 내려보내기**: 스포일러 유출과 불법복제로 이어진다.
- ❌ **음성 시간 무제한 + 무료 모델**: 中 업계는 음성 대역폭 비용을 수익화의 난제로 꼽는다. 비용 구조를 먼저 설계하라.
- ❌ **AI가 시나리오를 통째로 쓰는 것을 핵심 가치로 삼기**: 장르의 핵심은 사람 사이의 심리전이다. AI는 진행자, 대타, 검수자, 변주 생성 역할에 우선 쓴다.

## 5. 권장 도메인 모델 (초안)

```
User            id, nickname, trustScore, playedScenarioIds[], blockedUserIds[], mutedUserIds[], isBeginner
Scenario        id, title, playerCount, durationMin, tags{style: 추리|RP|감성|코미디|호러, beginnerOk}, authorId, status(draft|testing|published)
  Character     id, scenarioId, publicProfile, handout(PRIVATE), secrets(PRIVATE), goals
  Phase         id, scenarioId, order, type(read|intro|investigate|discuss|whisper|vote|ending), durationSec, revealRules[]
  Clue          id, scenarioId, content(PRIVATE), revealCondition
  Ending        id, scenarioId, condition, text
Session         id, scenarioId, state(lobby|precheck|running|paused_reconnect|ended|aborted), currentPhaseId, deposit
  Seat          sessionId, characterId, userId | aiAgentId, connectionState
  EventLog      sessionId, ts, type, visibility(all|seat:[...]), payload   ← 서버가 원본. 재접속 복원과 AI 컨텍스트의 소스
Rating          userId, scenarioId, deduction, rp, emotion, fairness, culpritFun, reasonTags[]
Report          reporterId, targetUserId, sessionId, reason
```

**세션 상태 머신 (핵심 경로):**
`lobby → precheck(REQ-P0-4) → running ⇄ paused_reconnect(REQ-P0-1) → [AI 대타 투입(REQ-P0-2)] → ended`
`running → aborted` 는 최후 수단이다. 보증금 정산(REQ-P0-3)과 원인 설문이 반드시 함께 일어나야 한다.

**AI 대타 컨텍스트 규칙:** `EventLog`에서 `visibility`가 `all`이거나 해당 seat를 포함하는 이벤트만 넣는다. 그리고 해당 `Character.handout`과 `secrets`를 넣는다. **다른 캐릭터의 PRIVATE 필드는 절대 포함하지 않는다.**
